# Product Documentation

This section explains **what Brk-Trkr is and how the product behaves** from a domain and user perspective.

Authoritative product documentation should live here when its primary purpose is to define product concepts, terminology, capabilities, workflows, policies, and domain behavior rather than implementation details.

## Planned structure

- `overview.md` — product purpose, scope, audiences, and capability map.
- `concepts.md` — core product and domain concepts.
- `glossary.md` — canonical terminology and definitions.
- `domains/` — domain-oriented product documentation such as catalog, owned assets, inventory, projects/builds, valuation, acquisition/disposal, storage/location, user management, and subscriptions.

## Content rules

- Describe current product behavior rather than implementation history.
- Keep implementation-specific database, API, and deployment details in Architecture unless they are necessary to explain product behavior.
- Use domain language consistently with the glossary.
- Surface explicit business rules and invariants where they materially define product behavior.
